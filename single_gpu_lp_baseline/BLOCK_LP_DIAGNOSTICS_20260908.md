# 有界连通块标签传播诊断与等时对照（2026-09-08）

## 范围与可复核配置

本轮只测试 `products`、`com-LiveJournal` 的 `k=4,8,32`，固定
`SEARCH_SEED=0`，`MAX_VERTEX_RATIO=1.10`。B 使用当前两轮连通块配置：

```ini
PAIR_EXCHANGE=0
BLOCK_LP=1
BLOCK_MAX_SIZE=16
BLOCK_SEEDS_PER_PAIR=8
BLOCK_FRONTIER_LIMIT=256
BLOCK_ROUNDS=2
BLOCK_VERIFY=0
GLOBAL_CYCLES=5
FIELD_ROUNDS=8
BALANCE_ROUNDS=5
POLISH_ROUNDS=20
```

A 只关闭 `BLOCK_LP`，其他配置相同。C 只关闭 `BLOCK_LP`，并统一使用
`GLOBAL_CYCLES=20`；这个周期数是固定规则，不按最终切边为单个案例调整。
它是“把相近时间继续花在原始 LP 上”的近似对照，不是严格的 wall-clock 截止器。

主程序计时不含读图和写盘。运行期间共享 GPU 上可能有其他任务，因此绝对墙钟数只作
本次环境下的对照；A/B/C 按相同机器、相同入口顺序测量。最终切边和容量均用
`verify_quality.py` 对完整 CSR 独立核验，表中的切边是无向切边；程序日志里的
`final_cut` 是双向 CSR 计数，等于表中数值的两倍。

## 逐轮机会与接受情况

`seed_pool` 是所有有向分区对中触碰目标标签的边界种子池，允许重复计数；
`start` 是真正送入 CUDA 增长 kernel 的种子数，受 `Q=8*k*(k-1)` 限制，分别为
96、448、7936。`positive` 是记录到正收益前缀的连通块数，`size>=2` 是其中
大小至少为 2 的数量。`select` 是通过顶点互斥和保守 incoming-only 容量筛选的块数；
最终 `accepted=1` 表示完整批次试标签的切边严格下降。`batch` 是块批次的即时无向
切边收益，`post` 是该批次后再次运行原有 polish/descent 的额外无向切边下降。

## 结论与唯一后续方向

诊断回答了“为什么有效或无效”：

- 机会存在且很丰富，尤其 k=32；非正种子长出正前缀的现象也被实际观察到。
- 当前顶点冲突淘汰不是唯一瓶颈；保守容量规则会淘汰大量候选，增长前沿扫描是主要成本。
- 块的即时收益有时能触发明显的后续 descent（例如 LiveJournal-k4/k32），但这种收益
  不足以抵消把相同时间直接继续用于 LP 的效果。
- 当前版本不值得继续扫桶大小、前沿大小或轮数，也不扩展更大的联合迁移。

若继续做一个后续实验，只选“降低候选增长/容量调度成本”的局部研究：保持块大小、种子
数量和正确性约束不变，先比较局部状态更新或更精确的容量候选排序；若仍不胜 C，则停止
两点/连通块这条支线，转向另一个有界联合迁移方向。当前 block LP 保留为默认关闭的可选
实验，不能据此宣称算法质量质变。
