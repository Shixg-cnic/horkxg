# 两点交换诊断与等时对照（2026-09-08）

## 实验范围

本次只跑 `products`、`com-LiveJournal` 的 `k=4,8,32`，固定
`SEARCH_SEED=0`。A/B/C 的其余搜索参数相同，`MAX_VERTEX_RATIO=1.10`：

| 版本 | 配置 |
| --- | --- |
| A 原始 LP | `PAIR_EXCHANGE=0`, `GLOBAL_CYCLES=5` |
| B LP＋交换 | `PAIR_EXCHANGE=1`, `PAIR_EXCHANGE_ROUNDS=2`, `PAIR_TOP_TARGETS=2`, `PAIR_BUCKET_LIMIT=32`, `GLOBAL_CYCLES=5` |
| C 延长 LP | `PAIR_EXCHANGE=0`, `GLOBAL_CYCLES=7`，统一增加两个周期 |

C 的 `5→7` 是所有案例统一使用的固定规则，没有按最终切边挑周期数；因此只能近似匹配 B 的时间。计时从主程序进入 `run()` 到输出前，未包含读图和写盘。运行期间 GPU 上有其他任务，墙钟时间会受干扰，不能把这些数字解释成独占 GPU 的基准。

输入约定是双向对称 CSR，加载器保留重复条目，因此平行边合法。配对公式中的 `adjacency(u,v)` 使用 CSR 中的边重数。输出切边和质量表均用独立的完整 CSR 校验，表中的切边是无向切边（程序内部 `cut` 的一半）。

## 正确性和实现检查

- `cmake --build build-gh200 --target single_gpu_lp_baseline -j2` 通过；当前计时字段只增加诊断输出。
- `python3 test_pair_exchange.py` 的小图测试覆盖满载交换、相邻端点的 `-2*adjacency` 修正、修正后拒绝、共享端点、跨交换邻接、孤立点、平行边、多分区候选和随机 CSR。
- `PAIR_VERIFY=1` 会在提交前用主机 CSR 验证提出配对收益，在提交后检查标签、负载、冲突和完整双向 cut；该验证已通过。
- 六组 B 输出再用独立完整 CSR 计算切边，并检查每点标签合法、最终负载和无向切边下降；没有发现状态不一致。
- `PAIR_EXCHANGE=0` 时不进入配对流程，A 的配置和输出路径仍是原始 LP。

## 诊断结论与唯一后续实验

主要现象是“机会足够但冲突淘汰严重”，尤其是高分区数：products-k32 的接受率为 2.1%–13.0%，LiveJournal-k32 为 0.9%–5.6%；k8 也大多只接受 2–9 个配对。k4 的冲突较轻。products 上配对后 descent 有时能继续下降，LiveJournal 的配对即时下降没有形成可观的后续下降；这说明交换并非普遍的停滞突破。当前实现的缓存重建成本也不是主要问题。

只选择一个后续实验：做一次固定配置的 GPU 冲突调度消融。候选生成、桶上限、两轮上限和容量约束全部不变，只替换当前保守的串行优先级贪心为 GPU 上的优先级局部竞争/有界 maximal-independent-set 选择；仍必须拒绝共享端点和不同交换端点之间的边，不能通过放松正确性约束换取接受数。该实验同时用 A/C 等时基线复核；若一次消融后 B 仍不胜 C，就停止继续扩展两点交换，转向有界连通小组迁移，不再做桶大小或轮数扫描。
